# 桌面端 RAG 知识库 · 实施方案 v2

> 本文档取代《离线化改造方案v1.md》。v1 中关于 fastembed 中文限制、LangChain API 变更等技术核查结论仍然有效，已并入本文档。
> 适用范围：Windows 桌面端 RAG 知识库，界面效果对标 Cherry Studio / WeKnora 级别。

## 1 方案概览

| 项目 | 选型 |
|---|---|
| 桌面壳 | **Electron**（自带 Chromium，打包体积约 160 MB） |
| 界面 | **Vue 3 + Ant Design Vue**（Web 前端，效果上限最高） |
| RAG 后端 | **Python + FastAPI**（本地服务，复用 Python RAG 生态） |
| 向量化 | `bge-small-zh-v1.5`（ONNX，本地离线） |
| 向量库 | Chroma（嵌入式持久化） |
| 关键词检索 | jieba + rank-bm25 |
| 重排 | `bge-reranker-base`（ONNX，可选开关） |
| 生成（本地） | llama.cpp `llama-server`（OpenAI 兼容接口） |
| 生成（云端） | OpenAI 兼容 API（百炼 / DeepSeek 等） |

### 1.1 为什么选 Electron 而不是 Tauri

两者界面效果**完全相同**——都是 Web 前端 + 桌面壳，Vue 代码一份不改。真正的差异在环境成本：

| | Electron | Tauri |
|---|---|---|
| 前置依赖 | **Node（本机已装 v24.19.0）** | Node + **Rust + MSVC（本机均未装）** |
| 额外安装量 | **0** | 5–7 GB |
| 打包体积 | ~160 MB | ~15 MB |
| 内存占用 | 200–400 MB | 50–100 MB |

本机 C 盘仅剩 17 GB，补装 Rust 与 MSVC 工具链成本高于运行时多占的内存。且 Electron 全栈 JS/TS，排错资料最丰富（Cherry Studio 即此路线）。

**打包体积 145 MB 的差异，换来的是零环境门槛与更低的维护成本。**

### 1.2 为什么 RAG 用 Python 而不是 Node

本机已装 `onnxruntime 1.28.0`、`langchain 1.3.11`、`pypdf 6.16.2`，Python 侧生态现成，不必从零搭建 Node 的 RAG 依赖链。

## 3 系统架构

```
┌──────────────────────────────────────────────────────┐
│  Electron (Node 主进程)                               │
│  ┌────────────────────────────────────────────────┐  │
│  │  渲染进程：Vue 3 + Ant Design Vue               │  │
│  │  知识库管理 / 对话 / 模型配置 / 设置             │  │
│  └────────────────────────────────────────────────┘  │
│          ↓ HTTP + SSE（localhost 动态端口）           │
│  ┌────────────────────────────────────────────────┐  │
│  │  Python 后端：FastAPI（子进程）                  │  │
│  │  解析 → 切片 → 双路索引 → 检索 → 融合 → 重排    │  │
│  └────────────────────────────────────────────────┘  │
│          ↓ 生成请求（OpenAI 协议）                    │
│  ┌──────────────────┬────────────────────────────┐  │
│  │ 本地 llama-server │ 云端 API（百炼/DeepSeek）  │  │
│  │ 127.0.0.1:8080    │ https://...               │  │
│  └──────────────────┴────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

### 3.1 进程模型

Electron 主进程启动时通过 `child_process.spawn` 拉起 Python 后端作为子进程，退出时一并关闭。

- **端口分配**：启动时动态选取空闲端口，经 IPC 传给渲染进程，避免端口冲突
- **通信分工**：前端直接向 Python 发 HTTP/SSE 请求（不绕 IPC）；IPC 仅负责端口传递与进程生命周期控制
- **进程清理**：监听 `window-all-closed` / `before-quit`，强制终止 Python 子进程，防止孤儿进程

### 3.2 数据流向与隐私边界

| 环节 | 是否离开本机 |
|---|---|
| 文档解析、切片 | ❌ 本地 |
| 向量化 | ❌ 本地（ONNX） |
| 向量库、BM25 索引 | ❌ 本地 |
| 检索、融合、重排 | ❌ 本地 |
| 生成（本地模式） | ❌ 本地 |
| 生成（云端模式） | ✅ 仅**命中的 top-K 片段** + 问题 |

**注意**：云端模式下，被检索命中的片段会发送至 API。这是"本地知识库 + 云端生成"的固有边界，界面上需明确提示用户当前处于哪种模式。

## 5 关键技术决策

### 5.1 中文 BM25 必须自建 ⚠️

fastembed 自带的 `Qdrant/bm25` 使用 `SimpleTokenizer`，分词逻辑等价于 `re.sub(r"[^\w]", " ", text.lower()).split()`。中文无空格，实测：

| 输入 | 分词结果 |
|---|---|
| `本产品的保修期是三年` | `['本产品的保修期是三年']` ← **整句变成一个 token** |

**结论**：该 BM25 对中文完全失效。稀疏检索侧必须用 `jieba` 分词 + `rank-bm25` 自建。经核验，fastembed 也未收录 `bge-m3`，SPLADE 仅有英文版，中文稀疏向量没有现成方案。

### 5.2 向量化用 ONNX，不用 torch

本机提交内存紧张，`torch` + `sentence-transformers` 体积超 2.5 GB 且运行期内存开销大。改用 `fastembed`（底层即 onnxruntime）加载 `bge-small-zh-v1.5`（约 95 MB）。

原方案选用的 `all-MiniLM-L6-v2` 是**纯英文模型**，中文知识库检索效果差，属选型错误。

### 5.3 RAG 编排用 LCEL

本机 langchain 为 1.3.11，`RetrievalQA` 已移出核心包，原文档代码会直接 ImportError。改用 LCEL：

```python
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)
```

### 5.4 双模式 LLM 只切 base_url

`llama-server` 与云端 API **都提供 OpenAI 兼容协议**，因此不需要写两套 LLM 代码：

| 模式 | base_url | api_key |
|---|---|---|
| 本地 | `http://127.0.0.1:8080/v1` | 任意占位符 |
| 云端 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 用户填写 |

本地服务启动命令：

```bash
llama-server.exe -m models/MiniCPM5-1B-F16.gguf -c 4096 -ngl 99 --port 8080
```

受 4 GB 显存限制，1B 模型可全量上卡（`-ngl 99`），3B 以上需下调 `-ngl` 或压小上下文。

### 5.5 本地模型选型

| 模型 | 显存占用 | 说明 |
|---|---|---|
| **MiniCPM5-1B**（已有） | ~2.2 GB (F16) | 实测 64 t/s，**先用它试水** |
| Qwen3-1.7B / Qwen2.5-1.5B-Instruct | ~1.2 GB (Q4) | 中文能力更强，后续可替换 |

本地模型定位是**文档问答**，不是通用助手。1B 模型做"基于给定片段回答问题"够用，复杂推理会吃力——这是容量决定的，不是配置问题。

### V3 / V4 未完全达标的说明

这两项依赖**向量检索**，而向量侧因 `huggingface.co` 与 `hf-mirror.com` 均不可达、模型下不下来而始终未能接入（即 P1 阻塞项）。当前召回完全由 jieba + BM25 单路承担，因此：

- **V4 的「语义场景向量命中」无法验证**，只有 BM25 一路。
- **V3 的「非仅字面匹配」部分达标**：词面能对上的中文提问召回正常（如「保修期是几年」命中得分 1.981）。
- 但纯 BM25 对**口语化提问**存在系统性短板，实测：

  | 查询 | 结果 | 原因 |
  |---|---|---|
  | `九十九元包邮` | ✅ 得分 3.807 | 词面完全匹配 |
  | `包邮吗` | ✅ 得分 1.269 | 分词正确 |
  | `满多少钱包邮？` | ❌ 无命中 | jieba 切出「钱包」，真正的关键词「包邮」被吃掉 |
  | `邮费怎么算` | ❌ 无命中 | 口语表述，字面与文档无交集 |

  这不是打包引入的问题——源码态同样复现，`retriever.py` 本轮未做任何改动。

**结论**：V3/V4 需等网络恢复、补上向量检索与 RRF 融合后才能完整通过。检索层接口已预留扩展点，补齐时上下游无需改动。

## 11 风险与对应

| 风险 | 说明 | 应对 |
|---|---|---|
| **打包体积** | Electron 自带 Chromium，约 160 MB | 可接受；如需瘦身可后续换 Tauri 壳 |
| **Python 打包** | PyInstaller 打包后体积大、启动慢 | 用 `--onedir` 模式；模型文件外置不入包 |
| **本地模型质量** | 1B 模型复杂推理吃力 | 定位为文档问答；保留云端切换 |
| **提交内存紧张** | 同时加载 embedding + rerank + LLM 可能失败 | 模型懒加载；rerank 做成开关 |
| **端口冲突** | 固定端口易被占用 | 动态分配端口，经 IPC 传递 |
| **子进程残留** | Electron 异常退出时 Python 可能变孤儿 | 监听退出事件强制清理 |
| **API Key 安全** | 明文存储有泄露风险 | 本地加密存储；不写入代码与日志 |
| **中文稀疏检索** | 无现成 ONNX 中文稀疏模型 | 已确定 jieba + rank-bm25 方案 |

**打包说明**

后端用 PyInstaller onedir 打成 `backend/dist/rag-backend/`，前端产物与后端 exe 经 electron-builder 的 `extraResources` 投放到 `resources/`（`files` 字段不支持 `../` 跳出项目根目录，跨目录资源只能走 extraResources）。

三处路径在打包后必须重定向，否则会静默出错：

| 位置 | 问题 | 处理 |
|---|---|---|
| `core/config.py` | `__file__` 冻结后指向 `_MEIPASS` 临时目录，用户知识库每次启动丢失且不报错 | 经 `RAG_DATA_DIR` 环境变量由主进程指定，独立运行时落到 `%APPDATA%/rag-desktop` |
| `electron/main.js` `BACKEND_DIR` | 指向 `app.asar` 内部，且 asar 里的 exe 无法被 spawn | 改用 `process.resourcesPath`，后端解包到磁盘 |
| `electron/main.js` `distIndex` | 同上 | 改用 `process.resourcesPath/frontend/dist` |

打包体积：安装包 154 MB，解压后 476 MB（后端 107 MB + Electron 运行时约 367 MB）。后端之所以只有 107 MB，是因为 chromadb / fastembed / onnxruntime / langchain 在代码中零引用，静态分析不会收进依赖图（`.venv` 有 516 MB）。注意 **numpy 不能排除**——`rank_bm25` 内部依赖它。

**P1 阻塞说明**：本机 `huggingface.co` 与 `hf-mirror.com` 均不可达（连接超时），bge-small-zh 的 ONNX 模型下载不下来，因此向量检索一路暂缺，当前检索由 jieba + BM25 单路承担。这是唯一偏离原计划的地方，其余功能不受影响。网络恢复后按「P1 → 向量检索 → RRF 融合」补齐即可，检索层接口已预留扩展点，上下游无需改动。
